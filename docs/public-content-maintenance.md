# Q-Gambit の公開案内を維持する

ガイド、FAQ、ルール、運営・問い合わせ・利用条件の説明を、実際のゲームと一致させ続けるための手順です。文章の量や更新日を増やすことを目的にしません。AdSenseの合否を自動判定する仕組みでもありません。

## 仕様変更時の確認

`docs/public-content-map.json` はゲーム操作、候補・勝敗、ヒント・時計、アカウント・接続・保存、販売・開示、公開ナビゲーションの変更と、確認する案内の対応表です。新しい利用者向け機能を追加する場合は、この対応表にも対象ソースと案内を追加してください。対応表は最低限の検知範囲で、すべての仕様差分を理解する代わりにはなりません。

1. 修正後、比較元を指定して確認用の下書きを作る。

   ```sh
   node scripts/release/content-maintenance.mjs --base origin/main --draft scratch/public-content-review-draft.json
   ```

2. 下書きの各ページ・見出しを、変更した仕様と実際の画面に照らして読む。必要なら日本語と英語の案内、商品説明、利用条件も揃える。操作が変わった場合は対応するブラウザー検証を行う。
3. 案内を修正するか、変更不要の具体的な理由を記録する。単に「確認した」ではなく、影響がない機能や条件、確認したコード・検証結果を記入する。
4. 実際の確認者、判断、根拠、確認ページが揃ってから `status` を `completed` にして、`docs/public-content-reviews/<変更名>.json` に保存する。
5. 関連するテストと次の確認を実行する。

   ```sh
   node --test scripts/release/content-maintenance.test.mjs scripts/qa/check-public-content.test.mjs
   node scripts/release/content-maintenance.mjs --base origin/main
   ```

`--head <commit>` を付けると、作業中のファイルではなく指定したコミットを検査します。PR用ワークフロー `verify-public-content.yml` はPRの比較元と先端を指定し、未確認・根拠不足・確認後のソース変更を失敗にします。既存のレビューを再利用する場合も、比較元と対象ファイルの内容が一致する必要があります。自動生成だけで確認済みになる記録は作りません。

ワークフローをmainへ取り込んだ後、GitHubでマージを必ず止めたい場合はブランチ保護の必須チェックに `guidance-review` を指定します。ワークフローの追加だけでは、このGitHub設定まで変更されません。

## 本番と週次の点検

```sh
node scripts/qa/check-public-content.mjs --report scratch/public-content-check.json
```

この処理は本番の8つの公開ページ、robots.txt、sitemap.xmlを読み、HTTP応答、初期HTMLのガイド・FAQ・例題・候補の連鎖、内部リンクと見出し、canonicalとindex設定を点検します。通信失敗とコンテンツの問題を区別し、一度だけ再試行します。結果と本文・リンクのダイジェストをJSONに保存します。既存の公開構成で必要な項目の回帰検査であり、記事数・文字数をGoogleの合格条件として扱うものではありません。

QUBEの説明形式を公開したことが確認できた後は、同じコマンドに `--require-qube` を付けて話者表示も確認します。公開前の本番へ新しい表示条件を適用しないでください。初期HTMLのマーカー確認だけで、全ての説明の帰属や実操作まで検証したことにはしません。

毎週月曜10時（日本時間）に、このチャットの定期点検で以下を行います。

1. 本番点検を実行し、直前に成功した結果と比較する。失敗した結果を正常な基準として上書きしない。
2. 公開案内やゲーム仕様に変更があれば、影響する見出しと日本語・英語の説明を実際に照合する。ルールや操作変更では関係するブラウザー検証も使う。UIや仕様の内容はこのHTTPチェックだけでは分からない。
3. 食い違いがあれば、担当する作業用コピーで修正し、検証と確認記録を残す。取り込みと本番反映はその時点の公開担当者に引き継ぐ。公開担当者の作業ディレクトリを勝手に編集しない。
4. 結果、未解決の問題、実際に行った修正を記録する。

変更がないときも、ヒントの条件、接続・保存、問い合わせ先、利用条件と最新の確認済みリリース情報が一致するかを点検します。新しい仕様の公開前に案内だけを先行させないでください。公開時点が未確認なら、確認が必要な候補として記録します。

ユーザーの関心や再訪は、本人の許可がある実データまたは実際のフィードバックで確認します。計測の有効化、架空の利用実績、架空の更新日・著者情報、毎週の水増し記事、AdSenseの再審査申請はこの処理に含めません。

Googleの品質指針やポリシーに変更があったときは公式ページを確認し、関係する案内を更新します。

- [Google パブリッシャー向けポリシー](https://support.google.com/adsense/answer/10502938)
- [Google ウェブ検索のスパムに関するポリシー](https://developers.google.com/search/docs/essentials/spam-policies)
