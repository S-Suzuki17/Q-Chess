## リリースを止める事項

1. 本番DBの `profiles` / `friends` / `active_matches` の許可範囲が広い。2026-09-24にカタログだけを読み取り確認。プロフィールの保護済み列は既存トリガーで守られるが、表示名などとフレンド行の所有者制限は不足。本人確認付きサーバーAPIへ移し、旧クライアントとの切替を検証してから権限を狭める。実ユーザーの行を書き換える実証はしない。
2. `register_user` / `login_user` / `update_user_email` は anon/authenticated が実行できる SECURITY DEFINER、search_path 未固定。直接RPCがHTTP側の連続試行制限を迂回する。サーバー経由への移行、最小権限、検索パス固定、回帰テストが必要。**旧Androidを壊す権限剥奪を先行しない。**
3. アカウント削除: ローカル実装・分離テスト済み部分はあるが、本番適用、画面操作検証、公開の削除案内、旧クライアント対策は未完了。
4. パスワード再設定: Resend無料枠を採用。承認済みDNS3件を追加し、権威DNSと公開DNSで値の一致を確認。Resend Verifiedを確認。旧キー2本が一覧から消え、新しいonboardingキー1本のみを確認して送信専用・ドメイン限定へ変更。ユーザーが新キーをSupabaseへ差替えた後、SMTP ON・保存済みパスワード表示・保存ボタン無効を確認した。秘密値は未取得。実送信試験は残る。既存 `profiles.email` は本人が検証済みと扱えないため、SMTPをつなぐだけでは既存パスワード口座の回復は完成しない。詳細は `smtp-setup-status-20260924.md`。
5. クラウン・サーキット進行はローカル中心。サーバー同期・ユーザー別分離・所有権検証を実装するまで、完全な端末間引き継ぎを宣伝しない。

## 公式資料と判断の境界

- [Supabase SMTP](https://supabase.com/docs/guides/auth/auth-smtp): 標準送信は本番用でなくチームのアドレスに制限される。
- [Resend + Supabase SMTP](https://resend.com/docs/send-with-supabase-smtp): 検証済みドメインとサーバー専用の秘密情報が必要。
- [Google Playのアカウント削除](https://support.google.com/googleplay/android-developer/answer/13327111?hl=en): アプリ内とWebからの削除要求導線を別々に確認する。
- [Supabaseユーザー管理](https://supabase.com/docs/guides/auth/managing-user-data): Auth削除だけで未失効JWTやStorageまで消えるとは扱わない。
- [Google Families広告](https://support.google.com/admob/answer/6223431?hl=en): 子供/年齢不明向けの広告ID・広告設定に配慮。
- [ICO保存期間](https://ico.org.uk/for-organisations/uk-gdpr-guidance-and-resources/data-protection-principles/a-guide-to-the-data-protection-principles/storage-limitation/): 保存目的に応じた期間が必要で、一律の「数か月保存」は保証された必須要件ではない。

これは技術監査。法令・ストア要件の全適合を保証する法律意見ではない。
